Headless Raspberry Pi Network Provisioning System with BLE Android App, Multi-Interface Failover and Cellular Support

IoT fleet deployment · Raspberry Pi + Go + Kotlin / Jetpack Compose

Problem
Pi-based devices ship with no monitor, keyboard or known network. Getting them online meant editing SD cards by hand, which non-technical users can't do at scale, and there was no reliable way to manage wired, Wi-Fi and cellular links once deployed.
Solution
A complete headless provisioning system I built end to end: an Android app (Kotlin / Jetpack Compose) sets up Wi-Fi over BLE through an AES-GCM encrypted channel keyed by a per-device PIN; a Go daemon manages Ethernet > Wi-Fi > LTE priority with per-interface health checks and automatic failover; and Python / Bash services on the Pi handle Bluetooth, cellular control and fleet features.
Full technical details
  • Encrypted onboarding at the application layer over BLE GATT (BlueZ) — secure without a pairing step
  • Cellular modem control through ModemManager; network configuration through NetworkManager; services run under systemd
  • USB reset key, event log with backup and restore, and automatic fallback to a USB Bluetooth adapter (udev)
  • Device names itself from its MAC and turns Bluetooth off once provisioned
  • Permission-tiered app screens to view interface IPs and set Ethernet to DHCP or static
  • Delivered as modular, documented source with a flashing guide, setup guide and flow diagrams; Soracom LTE ready
Raspberry PiPythonGoBash / systemd BlueZ BLE/GATTNetworkManagerModemManager Kotlin / Jetpack ComposeAES-GCMLTE
Outcome
Blank SD → online in minutes
No peripherals needed. Automatic failover across Ethernet, Wi-Fi and cellular, with fleet tools for reset, logging and recovery.

HeliosNet — Resilient Multi-Site Edge Network with Automatic Failover, LoRa SOS and Edge AI

Remote-site monitoring platform · Ubuntu gateways + ESP32-S3 nodes + mTLS MQTT

Problem
Remote sites need to stay online and monitored even when their internet link fails — and still be able to raise an emergency alert when every connection and gateway is down.
Solution
A complete edge networking system I designed and built. Each gateway (GMKtec M8S / Odroid H4, Ubuntu) continuously scores Ethernet, Starlink, Wi-Fi, dual LTE and Wi-Fi HaLow links and switches on its own measurements. Sites share internet over long-range Wi-Fi HaLow backhaul, ESP32-S3 sensor nodes report over mTLS MQTT, and a central HQ dashboard collects every site's events over Tailscale.
Full technical details
  • Secure by design: a certificate authority per site, mTLS MQTT (Mosquitto) with per-node access rules, one-command node enrolment, over-the-air updates that carry no secrets
  • ESP32-S3 sensor nodes (ESP-IDF): gas (MQ-2 / MQ-4, CO), CO₂, temperature and humidity, vibration, water leak and GPS, with calibration, health monitoring and threshold alerts
  • Emergency SOS over LoRa (Meshtastic) that works with no internet and every gateway off; GPS position shows on any Meshtastic phone
  • Dashboards: Guardian (live links, sensors, alerts) and a central HQ with offline queuing
  • Edge AI: NVIDIA Jetson Orin engine plus a local 3B LLM (llama.cpp) that explains alerts and summarizes events — advisory only, never controls the network
  • One-step deployment: USB auto-installer, or a single setup command each for gateways, consoles and AI nodes, with full deployment documentation
UbuntuPythonBashC / ESP-IDF DockerMQTT / MosquittoTLS / PKI NetworkManagerTailscaleLTE / Starlink Wi-Fi HaLowLoRa / MeshtasticJetsonllama.cpp
Outcome
3–6 s failover
Sites stay online across five link types with stable failback, and SOS alerts still get through with no internet at all.

Pizzomat v2.0 — Fully Automated Robotic Pizza Kiosk

European food-tech startup · Delta AS228T PLC + Electron HMI

Problem
A self-service kiosk storing 204 pizzas across 12 columns and 17 rows, baking on demand with dual IR ovens, cutting with an 8-blade press, and delivering through dual pickup windows — with zero human intervention, FIFO plus cloud-booked inventory, and six languages. No off-the-shelf solution existed; every layer had to be engineered from scratch.
Solution
Two parallel tracks: on the PLC, eight structured-text function blocks in ISPSoft — a 10-state master state machine, 4-channel PWM thermal control with soft-start for IR lamp protection, a unified FIFO/direct-address slot picker, 3-axis servo motion sequencing, cutter safety interlocks, a prioritized alarm manager, and an HMI watchdog. On the customer side, an eight-screen Electron + React touch HMI with six-language i18n, driven live by PLC state over an 80+ register Modbus TCP map.
Full technical details
  • Modbus Map v1.1 served as the single integration contract — handed to three downstream teams (cloud API, payment terminal, mechanical integration) enabling parallel development
  • Screens: advertising loop, language select, pizza selection, booking-code keypad, payment wait, live baking progress with real oven temperatures, delivery confirmation, fault display
  • 34 baking profiles (5 hard-coded + 29 OTA-updatable from cloud); architecture ready for EtherCAT servo integration without rework
  • All function blocks verified on the Delta AS200 simulator: state transitions, PWM ramps, FIFO selection, safety interlocks, alarm escalation

3 teams unblocked in parallel

VESC BLE-UART Bridge — Firmware Port to TI CC2540

Open-source motor controller ecosystem · Embedded C on 8051

Problem
VESC Tool's wireless link existed only for ESP32 and nRF52 — no firmware for the cheap, widely available TI CC2540, which uses a completely different proprietary BLE stack and offers just 8KB of RAM.
Solution
A complete firmware port implementing a transparent BLE-to-UART bridge: Nordic UART Service with 128-bit UUIDs and proper CCCD handling, interrupt-driven UART at 115200 baud, an event-based OSAL architecture, and careful buffer management within 20-byte BLE MTU and tight memory constraints.
Full technical details
  • GAP peripheral role with optimized advertising and connection parameter negotiation for low latency
  • Dynamic CCCD table allocation and clock division during idle for power efficiency
  • Delivered with documentation, hardware connection guides, a 12-point test validation suite, and LED status indication

BLE Channel Sounding Child-Proximity Locator

Wearable safety device · Nordic nRF54L15 firmware

Problem
Tracker tags based on RSSI only give a vague "near/far" — the goal was a parent unit and child tag with true distance ranging and an instant out-of-range alarm, with no phone, cloud, or GPS dependency.
Solution
From-scratch firmware on the nRF54L15 (Zephyr / nRF Connect SDK) using Bluetooth 6 Channel Sounding for phase/time-based ranging — multiple distance estimators (IFFT, phase-slope), tuned external antenna path for ~40 m line-of-sight, a flash-persisted configurable alarm (10–100 m thresholds), and dual-role BLE streaming distance, RSSI, and magnetometer heading to a phone over custom GATT.
Full technical details
  • Full serial shell for live tuning of threshold, ranging interval, antenna, TX power, estimator and buzzer
  • RSSI fallback that works at full BLE range when Channel Sounding drops — implemented via a vendor-specific controller command to work around an unsupported standard HCI command on the nRF54L15
  • LIS3MDL magnetometer heading with figure-8 hard-iron calibration streamed alongside distance
  • Diagnosed and fixed an I²C sensor-detection quirk and radio-time contention between simultaneous BLE roles

ESP32-S3 AI Robotic Arm — Vision-Guided Pick-and-Place

6+ DOF robotic arm · ESP32-S3 + camera + Windows AI server

Problem
A 6+ DOF robotic arm with a gripper is normally driven by fixed, pre-taught coordinates — it can't adapt when a target object moves. Real pick-and-place needs the arm to see where an object is and reach for it, but running vision AI and real-time motion control together is too heavy for a microcontroller alone.
Solution
A hybrid architecture split by strength. The ESP32-S3 handles camera streaming, real-time control of all six joints and the gripper, and lightweight on-device inference; a Windows application/server runs the heavier object detection, maps detected objects from camera space into arm coordinates, and streams motion commands back over WiFi — closing the loop from "see the object" to "grasp and place it."
Full technical details
  • ESP32-S3 firmware: camera capture/streaming, coordinated multi-servo motion for 6+ DOF, gripper actuation, and WiFi command interface
  • Hybrid AI: fast on-device inference on the S3 plus heavier detection on the PC server — each task runs where it belongs
  • Windows app/server: object detection, pixel-to-arm coordinate mapping, and a control/monitoring interface with live camera view
  • Closed-loop pick-and-place: detect target → compute reach → grasp → place, adapting to object position
ESP32-S3Camera / visionAI object detection Pick-and-place6+ DOF servosWindows app/server WiFi
Outcome
Vision-guided grasping
The arm detects an object, computes a reach, and picks and places it autonomously — driven from a Windows control & monitoring interface.
