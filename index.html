Headless Raspberry Pi Provisioning & Network Failover System

IoT fleet deployment · Python + Go + Kotlin

Problem
Pi-based IoT devices ship with no monitor, keyboard, or known network — getting them online meant editing SD cards by hand, impossible for non-technical users at scale, with no resilient way to manage wired, WiFi, and cellular paths after deployment.
Solution
A three-part system: a Python BLE service on the Pi receives WiFi credentials from an Android app over an AES-GCM encrypted channel (key derived from a per-device PIN); a dependency-free Go daemon manages connectivity with Ethernet > WiFi > LTE prioritization, per-interface health probing, and automatic failover; the device self-names from its MAC and disables Bluetooth once provisioned.
Full technical details
  • Application-layer AES-GCM encryption over BLE GATT — secure onboarding without pairing UX
  • Permission-tiered app feature to view interface IPs and reconfigure Ethernet (DHCP/static)
  • All settings live as editable files on the boot partition for fleet-friendly imaging
  • Delivered as modular, documented source with step-by-step flashing guide, Soracom LTE ready
Raspberry PiPython BLE/GATTGo Kotlin/AndroidAES-GCMLTE/Soracom
Outcome
Blank SD → online in minutes
Zero peripherals needed. Automatic, instant failover across Ethernet, WiFi and cellular; self-naming, self-securing on boot.

BLE Channel Sounding Child-Proximity Locator

Wearable safety device · Nordic nRF54L15 firmware

Problem
Tracker tags based on RSSI only give a vague "near/far" — the goal was a parent unit and child tag with true distance ranging and an instant out-of-range alarm, with no phone, cloud, or GPS dependency.
Solution
From-scratch firmware on the nRF54L15 (Zephyr / nRF Connect SDK) using Bluetooth 6 Channel Sounding for phase/time-based ranging — multiple distance estimators (IFFT, phase-slope), tuned external antenna path for ~40 m line-of-sight, a flash-persisted configurable alarm (10–100 m thresholds), and dual-role BLE streaming distance, RSSI, and magnetometer heading to a phone over custom GATT.
Full technical details
  • Full serial shell for live tuning of threshold, ranging interval, antenna, TX power, estimator and buzzer
  • RSSI fallback that works at full BLE range when Channel Sounding drops — implemented via a vendor-specific controller command to work around an unsupported standard HCI command on the nRF54L15
  • LIS3MDL magnetometer heading with figure-8 hard-iron calibration streamed alongside distance
  • Diagnosed and fixed an I²C sensor-detection quirk and radio-time contention between simultaneous BLE roles
nRF54L15Zephyr RTOSBluetooth 6 Channel Sounding GATTLIS3MDLC
Outcome
Real-time true ranging
Validated from ~1.5 m out to tens of metres, with a reliable distance-threshold alarm and live telemetry to a phone.

HeliosNet — Off-Grid LTE Gateway with Mesh & LoRa Bridge

Remote-site connectivity platform · ESP-IDF, 4 firmwares

Problem
Remote sites — farms, field equipment, disaster zones — need internet that survives link failures. Off-the-shelf LTE routers don't fail over gracefully, don't extend reach over low-power radio, and existing mesh/LoRa solutions don't interoperate cleanly.
Solution
A four-firmware ESP-IDF platform around a LILYGO T-SIM7600E-H gateway: three-tier WAN failover (Ethernet → LTE → mesh-only) with hysteresis and anti-flap; an auto-discovering ESP-NOW mesh with no hardcoded MACs; a LoRa bridge (SX1262) sharing one wire format with app-level ACK/retry; and an internet forwarding service so battery LoRa nodes hundreds of metres away can reach the web through the gateway's LTE uplink.
Full technical details
  • Live web dashboard: uplink status, battery, peer table, event log
  • Dual-partition OTA with rollback, AES-128-GCM payload encryption, persistent NVS configuration
  • Pure ESP-IDF v5.3.5 (no Arduino); hand-rolled SX1262 driver tuned to Heltec V3.2+ TCXO hardware
  • Vendor-neutral architecture — generic Ethernet WAN, cloud/MQTT phase is additive, not a refactor

Ultra-Low-Power BLE CO₂ Sensor Firmware

Battery-powered air-quality monitor · PhyPlus PHY6252

Problem
A custom Bluetooth CO₂ sensor had to run for months on a single CR2450 coin cell within a strict 75 µA average budget — starting from a bare SDK example with blocking calls, unreachable advertising, no mode switching, and no data persistence.
Solution
Complete firmware on the PHY6252: a dual-mode state machine (5-minute background sampling, 5-second live streaming on connection), a non-blocking OSAL sensor pipeline that never stalls the BLE stack, a circular RAM buffer with flash persistence, and a binary GATT sync protocol for efficient historical transfer — plus a hardware BOM error (wrong SHT40 I²C address variant) diagnosed and resolved through systematic debugging.
Full technical details
  • Automatic recovery to background mode on disconnect, error, or power cycle — data integrity preserved
  • STCC4 CO₂ controller interface debugging across the hardware/software boundary
  • Ready for mobile integration via Flutter app

Pizzomat v2.0 — Fully Automated Robotic Pizza Kiosk

European food-tech startup · Delta AS228T PLC + Electron HMI

Problem
A self-service kiosk storing 204 pizzas across 12 columns and 17 rows, baking on demand with dual IR ovens, cutting with an 8-blade press, and delivering through dual pickup windows — with zero human intervention, FIFO plus cloud-booked inventory, and six languages. No off-the-shelf solution existed; every layer had to be engineered from scratch.
Solution
Two parallel tracks: on the PLC, eight structured-text function blocks in ISPSoft — a 10-state master state machine, 4-channel PWM thermal control with soft-start for IR lamp protection, a unified FIFO/direct-address slot picker, 3-axis servo motion sequencing, cutter safety interlocks, a prioritized alarm manager, and an HMI watchdog. On the customer side, an eight-screen Electron + React touch HMI with six-language i18n, driven live by PLC state over an 80+ register Modbus TCP map.
Full technical details
  • Modbus Map v1.1 served as the single integration contract — handed to three downstream teams (cloud API, payment terminal, mechanical integration) enabling parallel development
  • Screens: advertising loop, language select, pizza selection, booking-code keypad, payment wait, live baking progress with real oven temperatures, delivery confirmation, fault display
  • 34 baking profiles (5 hard-coded + 29 OTA-updatable from cloud); architecture ready for EtherCAT servo integration without rework
  • All function blocks verified on the Delta AS200 simulator: state transitions, PWM ramps, FIFO selection, safety interlocks, alarm escalation

ESP32-S3 AI Robotic Arm — Vision-Guided Pick-and-Place

6+ DOF robotic arm · ESP32-S3 + camera + Windows AI server

Problem
A 6+ DOF robotic arm with a gripper is normally driven by fixed, pre-taught coordinates — it can't adapt when a target object moves. Real pick-and-place needs the arm to see where an object is and reach for it, but running vision AI and real-time motion control together is too heavy for a microcontroller alone.
Solution
A hybrid architecture split by strength. The ESP32-S3 handles camera streaming, real-time control of all six joints and the gripper, and lightweight on-device inference; a Windows application/server runs the heavier object detection, maps detected objects from camera space into arm coordinates, and streams motion commands back over WiFi — closing the loop from "see the object" to "grasp and place it."
Full technical details
  • ESP32-S3 firmware: camera capture/streaming, coordinated multi-servo motion for 6+ DOF, gripper actuation, and WiFi command interface
  • Hybrid AI: fast on-device inference on the S3 plus heavier detection on the PC server — each task runs where it belongs
  • Windows app/server: object detection, pixel-to-arm coordinate mapping, and a control/monitoring interface with live camera view
  • Closed-loop pick-and-place: detect target → compute reach → grasp → place, adapting to object position
ESP32-S3Camera / visionAI object detection Pick-and-place6+ DOF servosWindows app/server WiFi
Outcome
Vision-guided grasping
The arm detects an object, computes a reach, and picks and places it autonomously — driven from a Windows control & monitoring interface.
